01

The rendering model

The build log is the whole story:

npm run build
Route (app)                     Size  First Load JS
┌ ○ /                        83.7 kB         186 kB
○  (Static)  prerendered as static content

That ○ (Static) marker means Next.js runs every component once, at build time, and writes finished HTML to disk. A visitor's browser gets a file from a CDN — no server executes React per request, no database is touched. This is SSG (Static Site Generation).

Three rendering models
ModelHTML is madeCost per visitorUsed here
SSGonce, at build~zero — CDN serves a fileyes
SSRper request, on a serverCPU every timeno
CSRin the browser, after JS loadsblank page until JS runsno

SSG fits because nothing here is per-visitor: the content is a name, a job history, some projects — it changes when the file changes, not when someone loads the page. Computing that at request time would just be waste.

Ask back

"When would you have needed SSR instead?"

Anything shown per-visitor or that changes between requests — a logged-in dashboard, live inventory, personalised pricing. A portfolio never needs that.

Hydration — where static and interactive meet

The static HTML isn't the whole payload. React also ships a JS bundle (the 186 kB above) that boots in the browser and attaches event handlers to the DOM that's already there — that's hydration. The rule it enforces: the server's HTML and the client's first render must match exactly, or React discards the mismatch and warns. Two real fixes for that rule live in §04.

02

Server components vs client components

Most files in src/components/ open with "use client". A few don't — layout.tsx, page.tsx, Section.tsx, JsonLd.tsx, Icons.tsx. That line is the entire concept.

Server Components (the App Router default) run only during the build. Their code is never sent to the browser — they can't use useState or an onClick, because there's no browser to run them in yet.

Client Components render at build time and ship to the browser to hydrate, so they can hold state and respond to events.

src/components/JsonLd.tsx
// no "use client" — this whole function runs at build time only.
export function JsonLd() {
  const data = { "@type": "Person", name: site.name, /* … */ };
  return <script type="application/ld+json"
    dangerouslySetInnerHTML={{ __html: JSON.stringify(data) }} />;
}

Zero bytes of this function reach the visitor — its output is baked straight into the page's <head>. Compare ThemeToggle.tsx, which needs onClick and so must ship its JS in full.

Say this

"use client" doesn't mean "renders on the client" — it means "this component's code must also be sent to the browser". It marks a boundary, and everything imported below it is pulled into the client bundle too. That boundary is the whole lever for keeping bundle size down.

03

The data layer — one typed file

Every word on the site lives in src/data/content.ts as exported objects. Components import from it; there's no fetch, no API, no CMS.

src/data/content.ts
export const site = { name: "Shubham Jain", role: "…", github: "https://github.com/…" } as const;
export type Project = { slug: string; title: string; repo?: string; /* … */ };
export const projects: Project[] = [ /* … */ ];

as const makes every field a literal, readonly type — site.name isn't typed string, it's typed "Shubham Jain". And because Project is exported and shared by Work.tsx and CaseStudyModal.tsx, adding a required field breaks the build everywhere it's used until every project object supplies it.

The payoff shows up as a content-driven UI pattern used three times over: {'{site.github && (…)}'}. Set site.github to an empty string and every GitHub link disappears, sitewide, with no component touched.

04

Theming: CSS variables, not dark: everywhere

The naive approach is className="bg-white dark:bg-black" repeated on every element. This site declares the palette twice as raw channels and lets one class flip re-tint everything.

  1. globals.css stores each color as space-separated RGB channels: --c-bg: 251 250 247 under :root, redefined under .dark.
  2. tailwind.config.ts maps each variable into a Tailwind color: bg: "rgb(var(--c-bg) / <alpha-value>)".
  3. Components just write bg-bg, text-accent — no dark: variant anywhere.

Storing bare channels rather than a full rgb(...) string is the detail that makes it work: Tailwind splices its alpha placeholder in, so bg-accent/10 compiles to rgb(var(--c-accent) / 0.10) — a working translucent color. A complete rgb() string would make every opacity modifier silently fail.

next-themes toggles one class, class="dark", on <html>. Tailwind is set to darkMode: "class" to match. One flip re-resolves every variable — no re-render, pure cascade.

The two hydration bugs this creates

Flash of wrong theme. The server can't know a visitor prefers dark, so it builds one HTML file for everyone. next-themes injects a blocking script in <head> that reads localStorage and sets the class before first paint. That script mutates the DOM before React hydrates — which is exactly why layout.tsx carries:

src/app/layout.tsx
<html lang="en" suppressHydrationWarning>

That attribute is scoped to this one element and tells React "I know this will differ, don't warn." This is a very common interview question — now the answer is precise, not vague.

The toggle icon itself. At build time there's no way to know sun or moon. Rendering either guarantees a mismatch, so:

src/components/ThemeToggle.tsx
const [mounted, setMounted] = useState(false);
useEffect(() => setMounted(true), []);
// server render: mounted=false → empty button
// client first render: mounted=false → empty button → matches → hydrates
// effect fires → mounted=true → correct icon animates in
{mounted && (isDark ? <MoonIcon/> : <SunIcon/>)}

The general principle: render the server-safe version first, upgrade after mount. The button keeps a static aria-label and fixed size throughout so nothing shifts and screen readers are never left without a label.

05

The animation architecture

Every effect on the site is built from four reusable primitives sharing one easing curve — cubic-bezier(0.22, 1, 0.36, 1), defined once in Reveal.tsx — so the whole page moves in one voice.

Reveal — scroll-in, via IntersectionObserver

src/components/Reveal.tsx
<MotionTag
  initial={{ opacity: 0, y: 22 }}
  whileInView={{ opacity: 1, y: 0 }}
  viewport={{ once: true, margin: "0px 0px -12% 0px" }}
/>

whileInView uses the browser's native IntersectionObserver, not a scroll handler measuring positions. once: true means it fires and stops watching. StaggerGroup extends this with Framer's variant system — the parent declares staggerChildren: 0.08 and children just opt in, so they cascade without knowing their own index.

SpotlightCard — glow and tilt, off the render cycle

src/components/SpotlightCard.tsx
const spotlight = useMotionTemplate`radial-gradient(340px circle at ${'${mx}'}px ${'${my}'}px, …)`;

useMotionTemplate builds a live CSS string from motion values; as the pointer moves, the gradient's center follows. Tilt is computed the same pass and eased through useSpring. The performance point: motion values update outside React's render cycle — Framer writes to the DOM style directly, so moving your mouse over a card never triggers a re-render. Doing this with useState would re-render on every mousemove.

MagneticButton — restraint as a decision

src/components/MagneticButton.tsx
x.set(Math.max(-7, Math.min(7, relX * 0.28)));

Hard-clamped to ±7px. A button that leans 30px toward your cursor is a usability bug — you end up chasing it. Worth saying out loud: the interesting decision is the cap, not the effect.

CountUp — hand-rolled, on purpose

A Framer motion value would render fractional numbers mid-flight (43.7, then 44.2), and rounding digit widths jitters visibly. So this one runs its own requestAnimationFrame loop with an easeOutExpo curve and rounds to an integer every frame. Under reduced motion, it skips straight to the final number — every reduced-motion branch in this codebase shows the end state, never nothing.

06

The hero canvas: a real particle system

HeroCanvas.tsx is the most algorithmically substantial file in the repo — a constellation of nodes on <canvas> that links neighbours and reacts to the cursor.

Sharp on Retina, without overpaying elsewhere

src/components/HeroCanvas.tsx
const dpr = Math.min(window.devicePixelRatio || 1, 2);
canvas.width  = Math.floor(width  * dpr);   // backing store: device px
canvas.style.width = `${'${width}'}px`;         // CSS box: layout px
ctx.setTransform(dpr, 0, 0, dpr, 0, 0);

The backing store is sized in device pixels while the CSS box stays in layout pixels — that's the Retina-sharpness trick. Math.min(dpr, 2) is a deliberate cap: a 3× display would otherwise ask for 9× the pixels on a background effect nobody inspects closely.

Three forces per particle

src/components/HeroCanvas.tsx
p.x  += p.vx;                             // 1. drift
p.vx += (p.hx - p.x) * 0.00035;         // 2. spring back toward home
p.vx += (dx / d) * push * 0.1;          // 3. pushed away from the cursor
p.vx *= 0.986;                          // damping — bleeds off energy

Each particle remembers a home position and is weakly pulled back to it — without that, drift would eventually clump or empty the field. This is a hand-rolled spring-damper, the same math useSpring runs internally.

Honest complexity: O(n²), bounded on purpose

src/components/HeroCanvas.tsx
for (let i = 0; i < particles.length; i++)
  for (let j = i + 1; j < particles.length; j++) { /* link check */ }

Every pair is checked every frame — at the hard-capped 76 particles that's ~2,850 checks/frame, trivial for modern JS. But it's only fine because of the cap, not because the algorithm scales; thousands of particles would need a spatial grid or quadtree. One micro-optimisation that is present: distances are compared squared (d2 > LINK_DIST²) so Math.sqrt only runs for pairs that actually draw a line.

Ask back

Naming both the algorithm and where it breaks (interviewer: "what if you needed 5,000 particles?") demonstrates more than either half alone.

Canvas pixels can't inherit CSS — so it watches for changes

src/components/HeroCanvas.tsx
const mo = new MutationObserver(() => { accent = readAccent(); });
mo.observe(document.documentElement, { attributes: true, attributeFilter: ["class"] });

The canvas reads --c-accent straight off document.documentElement and watches for the theme class flipping, so the constellation re-tints on toggle. Light mode also gets a higher alpha multiplier — the same channel values would be nearly invisible against a bright background.

And the cleanup a junior dev forgets: the effect's teardown calls cancelAnimationFrame and disconnects both the ResizeObserver and the MutationObserver. Skip that and every theme change starts a second animation loop on top of the first — missing useEffect cleanup is the textbook answer when an interviewer asks you to spot a leak.

07

Scroll-spy and the sliding pill

Which section am I reading

src/lib/useActiveSection.ts
const line = window.scrollY + window.innerHeight * 0.32;
let current = "";
for (const section of sections) {
  if (section.offsetTop <= line) current = section.id;
}

An imaginary line a third of the way down the viewport — tuned to where a reader's eye actually sits, not the top edge. Two edge cases are handled explicitly, which is what separates a working implementation from a demo: at the very bottom of the page the last section is forced active (its top may never cross the line), and inside the hero nothing is marked active at all, so the pill doesn't cling to the first item. The scroll listener is registered {'{ passive: true }'}, promising the browser it won't call preventDefault() — scrolling never waits on it.

This logic used to live inside Nav.tsx. It moved into a module-level store (§11) once the hamster needed to know the section too: two separate listeners could disagree about which section is being read, one store can't. Measurements are coalesced to one per animation frame, and a ResizeObserver on <main> re-runs it when a section changes height with no scroll — switching Experience to its git-log view, or opening the terminal's output.

The pill itself: a shared layout animation

src/components/Nav.tsx
{active === item.id && <motion.span layoutId="nav-pill" />}

Only one pill element exists at a time; it unmounts from one link and mounts on another as active changes. Because both instances share layoutId="nav-pill", Framer treats them as the same logical element, measures before/after positions, and animates the difference with a spring — a gliding pill with zero position math written by hand.

08

Accessibility: not decorative

Focus trap in the case-study dialog

src/components/CaseStudyModal.tsx
const previouslyFocused = document.activeElement;
document.body.style.overflow = "hidden";
setTimeout(() => closeRef.current?.focus(), 60);
// on Tab: wrap last→first and Shift+Tab: wrap first→last
return () => previouslyFocused?.focus?.();

Tabbing past the last focusable element wraps to the first, and vice versa with Shift+Tab — keyboard focus never escapes into the page behind the dialog. Closing restores focus to whatever was focused before, which is the detail people miss; without it, a keyboard user gets dumped at the top of the document. The dialog also carries role="dialog", aria-modal="true" and aria-labelledby.

Two independent layers of motion safety

JS animations check useReducedMotion(). CSS-driven ones (a pulsing dot, a hover sheen) aren't visible to Framer, so globals.css carries a blanket override collapsing every animation and transition to near-zero duration under prefers-reduced-motion: reduce. Belt and braces — the site is fully usable and fully readable with motion off.

ScrambleText and the accessibility tree

The role line decodes from random glyphs on load. Done naively, that puts garbage in front of a screen reader and search engine while it animates. Instead the real string is present in the accessibility tree throughout, and reduced motion renders the final text immediately — the effect costs nothing in SEO or for assistive tech.

Also present: a "skip to content" link that appears on focus as the very first element in <body>, a global :focus-visible ring, aria-hidden on every decorative element, and rel="noopener noreferrer" on external links.

09

Performance decisions, and why

  • Self-hosted fonts via next/font/local — no third-party request to Google, no extra DNS/TLS round trip before first paint, and the build works with no network access. display: "swap" shows the fallback face immediately rather than hiding text.
  • Motion values over React state for pointer tracking — no re-render per mousemove (§05).
  • IntersectionObserver over scroll math for reveals — native, off the main thread (§05).
  • once: true everywhere an observer is used — nothing keeps watching after it fires.
  • Passive scroll listener in the nav — never blocks the browser's scroll thread.
  • Bounded canvas cost — DPR capped at 2, particles capped at 76 (§06).
  • Server Components for non-interactive parts — JsonLd and Icons ship no JS at all (§02).

SEO surface

layout.tsx exports a metadata object — Next's file-based metadata API — generating the title, description, OpenGraph tags (link previews in Slack/LinkedIn/iMessage) and Twitter card tags. title.template would auto-suffix any future page's title with the site name.

sitemap.ts and robots.ts are functions that run at build time and produce real /sitemap.xml and /robots.txt files — both read site.url from the content file, which is why that field has to match the real domain after deploying.

JsonLd.tsx emits schema.org Person structured data — worksFor, alumniOf, knowsAbout built straight from the skills array — so Google can render a rich result on a name search. It's a Server Component, so it costs zero client-side bytes (§02).

Shared stores and the hamster's day

Two tiny external stores, not Context

src/lib/useHamsterCount.ts
/** How many times the hamster has been fed today, in this browser. 0 on the server. */
export function useHamsterCount(): number {
  return useSyncExternalStore(subscribe, () => count, () => 0);
}

The feed count is shown in three places — the hamster's pill, the status footer and the terminal's hamster command — and they must agree the instant a feed happens. The obvious tool, the storage event, never fires in the tab that did the writing, so each consumer reading localStorage itself would lag. Instead one module holds the value and a set of listeners; useSyncExternalStore subscribes each component, and the third argument is the server snapshot, so the static HTML renders 0 without a hydration mismatch. The store also keeps a mirror of the last value it read or wrote, because in a browser with site data blocked even reading localStorage throws — the count still works for that visit. useActiveSection.ts is the same pattern for the scroll-spy.

Why not React Context? Context would force a provider high in the tree and re-render its subtree on every change. These are two primitive values read by a handful of leaf components — an external store is the smaller tool.

Sleep as a pure function

src/lib/hamsterCount.ts
export function isAsleep(now: Date, lastActivity: number | null): boolean {
  if (!isNightHour(now)) return false;
  return lastActivity === null || now.getTime() - lastActivity >= AWAKE_IDLE_MS;
}

Between 23:00 and 06:00 in the visitor's own timezone the hamster opens asleep; only a click wakes it, and any activity on the page then keeps it up until two idle minutes pass. Keeping the rule free of React and of new Date() means it was checked with plain Node scripts at 22:59, 23:00, 05:59 and 06:00 — and each check was proven able to fail by breaking the function on purpose.

A bug the verification found: wall clocks go backwards

src/components/Hamster.tsx
// Monotonic, so a clock set back (DST, a manual change) can't lock feeding out for hours.
const tick = performance.now();
if (busy.current || tick - lastFeedAt.current < MIN_FEED_GAP_MS) return;

Feeds are spaced at least 400ms apart so a held Enter key can't flood the count. The first version measured that gap with Date.now(); a browser test that moved the clock from 23:30 back to 14:00 then found the hamster refused to eat — the "last feed" was nine hours in the future. performance.now() only ever increases, so it's the right clock for intervals; wall-clock time is still used where it means something (is it night?).

One state machine, explicit priorities

src/components/Hamster.tsx
// One thing on its head: sleep beats the section, and the section beats the theme.
const headwear: Headwear | null = asleep
  ? "nightcap"
  : section === "experience"
    ? "hardhat"
    : resolvedTheme === "light"
      ? "sunglasses"
      : null;

Sleep, chewing, the every-fifth-feed stash walk, section props, theme accessories and the "thrilled" reaction to Email/Résumé links all compete for one small drawing. Writing the priority down as a single expression is what stops impossible combinations — a hard hat on a sleeping hamster, a laptop held while it eats. The Email/Résumé detection ignores touch (a tap has no pointerout, so the state would stick), ignores links under the modal, and compares the parsed URL's pathname rather than building a CSS selector from content. Sunglasses sit pushed up on the forehead so they never cover the eyes that follow the cursor — and, for keyboard users, follow focus.

The whoami terminal and the alternate views

A terminal that can't be injected

src/lib/terminal.ts
// A plain substring match: what's typed is never turned into a RegExp.
const grep = command.match(/^skills ?\| ?grep (.+)$/);

The hero's thesis card doubles as a terminal: whoami, experience --current, skills | grep postgres and friends. runCommand is a pure function of the content file that returns text parts — never HTML — and React renders them as text, so typed markup comes back as literal characters. Unknown commands never echo the input (so nobody can screenshot the site "saying" something), commands match case-insensitively because phones capitalise the first letter, and → completes while Tab keeps its normal job of moving focus.

The thesis stays pinned above the prompt and is part of the server HTML, so crawlers, link previews and anyone who never types read exactly what the card said before. The design rule was "at most +24px taller than the old card"; the first build measured +97px, so it went back to the owner, who chose a compact layout: +28px on desktop, tap-to-run example chips only on phones, and an output area that opens on the first command rather than reserving empty space at page load.

Views that reuse facts instead of inventing them

  • Status footer (StatusBoard.tsx) — "All critical systems operational" over rows that are facts already on the site (availability, location), the hamster's live count, and coffee: degraded. No uptime bars: varied bars would be made-up history.
  • git log view of Experience — one straight line of commits, newest first, degree as the root. A branch and merge would have claimed parallel work that never happened. Hashes are a stable FNV-1a of each role's words (identical on server and client) and aria-hidden, so a screen reader hears title, company, period, tech. The timeline is hidden rather than unmounted while git log shows, so Framer's useScroll keeps its target and the drawn rail survives the round trip.
  • Postmortem view of the Kaveri case study only — the one project whose problem was a production slowdown. Impact is the outcome, Root cause the problem, Fix the steps taken, all word for word; no invented timeline or lessons.
13

Questions to be ready for

Why Next.js, not plain React (Vite / CRA)?

Static prerendering, file-based routing, built-in metadata/sitemap APIs, next/font optimisation, zero-config Vercel deploys. Plain React would ship a near-empty HTML shell and render everything client-side — worse for SEO and slower first paint on a content-first site like this.

Why not just plain HTML and CSS, then?

Fair pushback, worth partly conceding. Componentisation plus one typed content file is what makes the case-study modal, the theme system and the scroll interactions maintainable — by hand that's a lot more code. But it's a real trade: 186 kB of JS for what is fundamentally a document. The counter is that the HTML renders and is fully readable before any of that JS ever arrives.

What's the biggest weakness of this site?

Bundle size for a document; an O(n²) canvas loop that only works because of a hard particle cap; no test runner (the logic is checked by one-off Node scripts, not a suite); no CI. Naming a real weakness lands better than claiming there isn't one.

Walk me through what happens when someone visits.

CDN returns prebuilt HTML → the blocking theme script sets the dark class before first paint → the browser paints fully-styled, readable content → JS downloads → React hydrates and attaches handlers → effects run: the canvas starts, the scroll listener attaches, IntersectionObservers arm → interactions go live.

Where does state actually live?

Mostly minimal and local. Work holds selected: Project | null for the modal; Nav holds scrolled/open; the terminal keeps its output and history in component state. Theme lives in next-themes's own context. Exactly two values are shared across distant parts of the tree — the section being read (nav pill and hamster props) and today's feed count (hamster, footer, terminal) — and each is a tiny module-level store read through useSyncExternalStore (§11). No Redux, no Zustand, no custom Context: two primitives don't justify a state library.

How would you add a blog to this?

src/app/blog/[slug]/page.tsx with generateStaticParams() to enumerate posts at build time — still fully static, and title.template already handles per-post titles.
